# Checklist: Pre-Completion

상세 절차·출력 예시는 `.harness/prompts/pre-completion-self-verify.md`를 참고합니다. 아래 항목이 해당 없으면 완료 보고에 **N/A와 이유**를 적습니다.

## 자기 검증

- [ ] 원래 요청과 최종 결과를 비교했습니다.
- [ ] 변경 파일과 변경 의도를 다시 확인했습니다.
- [ ] 관련 테스트, 린트, 타입체크, 빌드 또는 수동 검증을 실행했습니다.
- [ ] 서버 프로세스(백엔드·API·워커 등)를 수정했다면 완료·검증 전에 해당 서버를 재시작했습니다(해당 없으면 N/A와 이유).
- [ ] 검증을 실행하지 못한 경우 정확한 이유와 대체 확인 방법을 기록했습니다.
- [ ] 검증이 있는 작업이라면 검증 명령·출력을 `docs/validation/` 증거 파일로 기록했고(`scripts/new-artifact.ps1 -Type validation`), 완료 보고 마지막 줄이 `EVIDENCE_RECORDED: <경로>`입니다(문서만 바꾼 작업은 `N/A(docs-only)`).
- [ ] 실패 로그가 있었다면 마지막 줄만 보지 않고 원인 맥락을 확인했습니다.
- [ ] 같은 파일을 **세 번 이상** 고쳤거나, 같은 검증이 **두 번 이상 같은 이유로** 실패했다면 요구사항 해석·파일 책임·테스트 신호와 원인 가설을 다시 세우고 접근을 재검토했습니다.
- [ ] 새 정보 없이 같은 명령만 반복 실행하지 않았습니다.
- [ ] run log를 남겨야 하는 작업인지 판단했습니다. 하네스·자동화 문제로 반복 실패했다면 run log와 `docs/LEARNING_LOG.md`·자동화 후보 여부를 검토했습니다.
- [ ] `docs/QUALITY_SCORE.md`의 **Minimum Passing Standard**를 한 번 대조했습니다(해당 없으면 N/A).
- [ ] 출력·diff·문서에 `.env`, 토큰, API 키, 계정 정보 등 민감정보가 들어가지 않았습니다.
- [ ] UI·스타일 파일을 수정했다면 `docs/UI_RULES.md` §5 체크리스트를 전부 대조하고 §6 배선 확인을 수행했습니다(해당 없으면 N/A).
- [ ] 화면의 룩이 바뀌는 UI 작업이라면 §5a 전후 사진 비교(3개 화면 크기 캡처·diff)를 수행하고 결과 위치를 `검증`에 남겼습니다(도구 없으면 수동 스크린샷 + 그 사실 기록, 해당 없으면 N/A).
- [ ] 이번 작업에서 만든 문서 산출물이 `docs/ARTIFACTS.md`의 위치·네이밍 규칙을 따릅니다(해당 없으면 N/A).

## exec-plan·실행 계획

- [ ] 기능 추가 또는 기능 동작 변경이라면 코드 변경 전에 active exec-plan을 만들거나 갱신했는지 확인했습니다.
- [ ] 작업 중 발견한 새 기능 범위를 plan 없이 바로 구현하지 않았는지 확인했습니다.
- [ ] exec-plan의 `Depends On`, `Blocks`, `Parallel Work`를 확인했습니다.
- [ ] `Partial` 또는 `Blocked` 상태라면 독립 완료 범위, 보류 범위, 보류 이유, 재개 조건을 기록했습니다.

## PRD 기능 계약·회귀

- [ ] 변경이 기존 PRD 기능 계약에 닿는지 확인하고 영향받은 기능을 기록했습니다.
- [ ] 기능 동작, UI 흐름, API/data, 권한/네비게이션이 바뀐 Feature ID의 `Current expected behavior`, `Regression scenario`, `Last updated by`, `Contract status`를 최신화했습니다.
- [ ] 전체 PRD 기능 테스트를 실행했다면 `Contract status=Current`인 기능만 대상으로 삼았습니다.
- [ ] 수정된 기능 계약이 `Needs update`인 상태에서는 전체 PRD 기능 정상 작동 테스트를 완료로 선언하지 않았습니다.
- [ ] 영향받은 기존 PRD 기능의 자동 테스트 또는 수동 회귀 시나리오를 실행했습니다.
- [ ] 동작·UI·shared state·API·data·navigation·auth/permission 변경이 있다면 `docs/TESTING.md`의 회귀 검증 기준을 확인했고, 기존 기능 회귀 확인 없이 완료로 선언하지 않았습니다.

## 문서·인덱스

- [ ] 문서 구조·인덱스·교차 참조를 바꿨다면 `.harness/checklists/doc-update.md`를 확인했습니다(해당 없으면 N/A).

## 버전 관리

- [ ] 검증 상태에 따라 `scripts/recommend-version-control.ps1`의 `Commit` 판단을 확인했습니다.
- [ ] exec-plan 없이 구두로 처리한 direct work unit도 자동 커밋 대상인지 확인하고, `hold`이면 이유를 기록했습니다.

## 완료 보고 형식

- [ ] 완료 보고가 표준 섹션 순서를 따릅니다: 요청 확인, 변경 사항, 검증, 결과 확인, CodeHealth, 리스크와 다음 판단.
- [ ] 시각화 위젯 도구를 쓸 수 있는 환경이면 완료 보고 핵심(변경 요약·검증 결과·리스크)을 **비쥬얼라이즈 위젯으로 함께** 보고했습니다. 도구가 없으면 마크다운 표로 대체하고 이유를 한 줄 남겼습니다.
- [ ] `리스크와 다음 판단`(남은 리스크·사용자 결정 사항)과 `추천 작업`(다음 할 일 제안·우선순위)도 텍스트 나열이 아니라 **비쥬얼라이즈 위젯**으로 표현했습니다(도구 없으면 마크다운 표 + 이유 한 줄).
- [ ] 모든 위젯 맨 위에 한 줄 제목을 넣었고, 보고 전체가 쉬운 말 규칙(전문 용어·변수명에 괄호 한글 병기)과 `.harness/reporting.json`의 현재 비유를 따랐습니다.
- [ ] `리스크와 다음 판단`·`추천 작업` 위젯의 각 안건에 실행 버튼(`sendPrompt`, 라벨 끝 ↗)을 넣었고, `reporting.json`의 `styleGuide`가 지정되어 있으면 그 가이드의 골격·언어 규율을 따랐습니다.
- [ ] `요청 확인`에 원래 요청과 최종 결과 충족 여부를 적었습니다.
- [ ] `변경 사항`에 변경 파일과 변경 의도를 적었습니다.
- [ ] `검증`에 아래를 빠짐없이 반영했습니다(해당 없으면 N/A).
  - 실행한 검증
  - 실행하지 못한 검증(이유·대체 확인)
  - 검증 표면: CLI / UI / 둘 다
  - 독립 완료 범위, 보류 범위, 보류 이유, 재개 조건
  - exec-plan 선행 여부
  - 기능 계약 최신화 여부
  - 기존 PRD 기능 회귀 확인
- [ ] `결과 확인`에 preview path, export command, UI location 등 사용자가 결과물을 확인할 위치를 적었습니다.
- [ ] `CodeHealth`에 errors, warnings, intentionally accepted warnings를 분리했습니다.
- [ ] `리스크와 다음 판단`에 남은 리스크·미검증 영역, 반복 루프 신호, run log 필요 여부, 확인하지 못한 부분, 사용자 결정 사항을 적었습니다.
