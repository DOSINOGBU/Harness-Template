# First Prompt

아래 프롬프트는 PRD를 작성한 뒤, 범용 buildproof 하네스를 프로젝트용 하네스로 초기화할 때 사용합니다.

중요한 점은 바로 코드를 구현하지 않고, 먼저 PRD를 하네스 문서로 분배하게 하는 것입니다.

```text
이 저장소는 범용 buildproof 하네스를 기반으로 새 프로젝트용 하네스를 만드는 단계야.

먼저 코드를 구현하지 말고, 아래 순서로 PRD를 프로젝트 하네스 문서에 반영해줘.

1. `AGENTS.md`, `docs/README.md`, `docs/WORKFLOW.md`를 읽고 현재 하네스 구조를 파악해줘.
2. `docs/PRD.md`를 제품 요구사항 원본으로 읽어줘.
3. PRD 내용을 아래 문서에 역할별로 분배해줘.
   - `docs/PRODUCT_CONTEXT.md`
   - `ARCHITECTURE.md`
   - `docs/PROJECT_RULES.md`
   - `docs/DATA.md`
   - `docs/SECURITY.md`
   - `docs/FRONTEND.md`
   - `docs/BACKEND.md`
   - `docs/TESTING.md`
   - `docs/OBSERVABILITY.md`
   - `docs/RELIABILITY.md`
   - 필요하면 `docs/DEPLOYMENT.md`, `docs/COST.md`, `docs/RUNBOOK.md`

3a. UI가 있는 프로젝트라면 `docs/UI_RULES.md`를 프로젝트 디자인 시스템으로 커스터마이즈해줘.
   - 상단 "하네스 적용 안내" 블록의 지시대로 `PROJECT-CUSTOMIZE` 표시 섹션(디자인 토큰 값, 폰트, 아이콘·컴포넌트 패키지명)을 PRD의 디자인 요구에 맞게 교체해줘.
   - 규칙 구조(강제 규칙, 토큰 계약, 체크리스트)는 유지하고 값만 바꿔줘.
   - `.harness/config.json`의 `validation.uiConformance.forbiddenPatterns`(하드코딩 색 등 금지 패턴 grep)도 교체한 토큰 체계에 맞게 조정해줘.
   - `docs/UI_RULES.md` §5a의 전후 사진 비교(시각 QA) 도구를 프로젝트 스택에 맞게 준비해줘(예시 구현: tradepilot `scripts/ui-visual-qa.mjs`, Playwright 3개 뷰포트 캡처 + 픽셀 diff).
   - UI가 없는 프로젝트라면 `validation.uiConformance.enabled`를 `false`로 바꿔줘.

4. PRD에서 모호한 부분, 위험한 결정, 나중에 확인해야 할 질문을 정리해줘.
5. MVP 구현을 위한 작업 단위를 `docs/exec-plans/active/` 아래에 작은 계획 문서로 나눠줘.
6. `scripts/init-testing-commands.ps1`를 dry-run으로 실행해서 테스트 명령 감지 결과를 보고해줘.
7. 마지막에 다음을 보고해줘.
   - 반영한 문서
   - PRD에서 하네스로 옮긴 핵심 결정
   - 아직 사람이 결정해야 할 질문
   - 바로 구현해도 되는 작업 단위
   - 실행한 검증과 남은 warning

중요:
- 아직 기능 구현은 하지 마.
- PRD 내용을 문서에 그대로 복붙하지 말고, 각 문서 목적에 맞게 요약/분배해줘.
- 모호한 요구사항은 임의로 확정하지 말고 assumption 또는 open question으로 남겨줘.
```

## 사용 타이밍

- `docs/PRD.md` 작성 직후
- 새 프로젝트에 buildproof 하네스를 처음 적용할 때
- 구현 전에 문서, 계획, 검증 기준을 먼저 정리하고 싶을 때

## 사람이 확인할 것

- AI가 PRD를 잘못 해석한 부분이 없는지 확인합니다.
- `open question`으로 남긴 항목 중 제품 방향에 중요한 것을 먼저 결정합니다.
- `docs/exec-plans/active/`에 생성된 작업 단위가 너무 크면 더 쪼개도록 요청합니다.
